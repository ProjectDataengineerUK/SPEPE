## Lições Aprendidas

### Processo

**O que funcionou bem:**

- **Ciclo SDD iterativo** — O modelo de iterate em cima de DEFINE/DESIGN acumulou
  inteligência de forma rastreável. Cada versão (v1→v4.6) tem contexto claro de
  por que foi feita.
- **BUILD REPORT como artefato de fase** — Ter o BUILD REPORT separado do DESIGN
  forçou a materialização do que foi efetivamente entregue vs. o que foi projetado.
- **Análise completa pós-ciclo** — A revisão do ciclo em 2026-04-30 revelou que o
  DESIGN havia evoluído (v4.2→v4.6) após o BUILD, com código implementado mas sem
  rastreabilidade. O SHIP forçou a correção.

**O que melhorar:**

- **Sincronizar BUILD REPORT ao evoluir o DESIGN** — Quando o DESIGN foi de v4.2 para
  v4.6 após o BUILD, o BUILD REPORT não foi atualizado. Regra para próximos projetos:
  todo `/iterate DESIGN` que adiciona MUST goals deve gerar um BUILD REPORT delta.
- **Open Questions têm shelf life** — A Open Question 3 (cobertura mínima SP) foi
  aberta em 2026-04-17 e nunca formalmente fechada. Adicionar deadline explícito ao
  criar Open Questions.
- **CLAUDE.md desincronizou do BRAINSTORM** — O roadmap no CLAUDE.md ficou na versão
  original (Fase 1 = TSE+IBGE) enquanto o BRAINSTORM evoluiu para 10 módulos em Fase 1.
  Manter CLAUDE.md como fonte canônica sincronizada com o último BRAINSTORM.

### Técnico

**O que funcionou bem:**

- **Fallback in-memory para GCP** — Todos os componentes (KnowledgeBase, MemoryManager,
  SemanticCache) implementam fallback local. Permite desenvolvimento e testes completos
  sem GCP ativo.
- **Sentinel com design modular** — A separação em 4 crews + watchers + KB separados
  torna cada componente testável de forma isolada. Os 28 testes cobrem todos os paths
  críticos sem GCP.
- **DESIGN como contrato executável** — O File Manifest do DESIGN (25 arquivos do
  Sentinel com responsabilidades e dependências explícitas) funcionou como spec de
  implementação. Zero ambiguidade sobre o que construir.
- **Firestore como fallback** — Usar Firestore em vez de Vertex AI Vector Search para
  o MemoryStore no MVP foi a decisão correta. Vertex AI seria bloqueado por GCP;
  Firestore permite validar o fluxo completo localmente.

**O que melhorar:**

- **Vertex AI Vector Search como upgrade de GCP** — A migração memory_store →
  Vertex AI Vector Search deve ser o primeiro componente a ser ativado após
  `terraform apply`. Criar task dedicada para isso no ciclo de deploy.
- **Sentinel precisa de `main.py`** — O Cloud Run do Sentinel aponta para
  `sentinel.main` mas o arquivo não existe ainda. Criar antes do deploy.
  (Pendência técnica registrada abaixo.)
- **DESIGN menciona `realtime_dq.py` (Dataflow streaming)** — Implementado como
  batch em `dataops/dq/runner.py`. Streaming Dataflow é Fase 2 — documentar
  explicitamente como out-of-scope para v1.0.0.

### Ferramentas

**O que funcionou bem:**

- **pytest com fallback in-memory** — Testes completos sem dependências externas.
  Padrão `_init_firestore()` / `_init_client()` com try/except + logger.info
  é o padrão certo para todos os clientes GCP.
- **Terraform por domínio** — 22 arquivos .tf com separação clara (sentinel.tf,
  pubsub_sentinel.tf) torna revisão e debugging muito mais fácil que um único main.tf.

## Próximo passo: Deploy GCP

Com o SHIP concluído, a sequência para v1.0.0 é:

```bash
# 1. Criar sentinel/main.py (entry point Cloud Run)
# 2. Build e push Docker
docker build -t spepe:$(git rev-parse --short HEAD) .
docker push southamerica-east1-docker.pkg.dev/$PROJECT_ID/spepe/app:$(git rev-parse --short HEAD)

# 3. Terraform apply
cd infra/terraform
terraform init -backend-config="bucket=$PROJECT_ID-terraform-state"
terraform plan -var="project_id=$PROJECT_ID" -var="app_image=..."
terraform apply

# 4. Ingestão SP (1 UF — smoke test)
gcloud run jobs execute tse-ingest --args="--uf SP --year 2022"
gcloud run jobs execute ibge-sync --args="--uf SP"
gcloud run jobs execute silver-transform --args="--uf SP --year 2022"
gcloud run jobs execute gold-build

# 5. Smoke test
curl https://$CLOUD_RUN_URL/health
# Validar: 7 agentes OK, budget guard ativo, disclaimers presentes

# 6. Tag v1.0.0
git tag v1.0.0
git push origin v1.0.0
```
